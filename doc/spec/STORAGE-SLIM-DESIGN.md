# 저장 용량 줄이기 설계

> 기준일: 2026-10-25 · 구현: `src/lib/data/slim-persist.ts`, `src/lib/data/storage-usage.ts`, `src/components/storage-usage-notice.tsx`

## 1. 배경

물건 데이터는 브라우저 localStorage에 JSON 한 덩어리로 저장된다. 브라우저 한도는 보통 약 5MB(5,242,880자)인데, 물건 36건이 약 549만 자로 한도에 거의 닿았다. 한도를 넘으면 문서 글자를 줄여 저장하는 비상 동작이 시작된다.

## 2. 측정 (물건 36건, 약 549만 자)

| 항목 | 비중 | 물건당 | 내용 |
|---|---|---|---|
| 리모델링 시나리오 | **49%** | 약 75,000자 | 3단계 시나리오가 물건마다 기본 카탈로그 복제본. id·시각만 빼면 36건이 전부 동일 |
| 원문 문서 정보 | 12% | 약 19,700자 | |
| 태인 보고서 표 | 9% | 약 14,100자 | |
| 체크리스트 | 9% | 약 13,800자 | 문구가 전 물건 동일한 기본 템플릿 |
| 권리분석 | 8% | 약 13,000자 | 그중 원문 글자(`rawText`)가 절반 |

## 3. 설계: 저장할 때만 기본값을 뺀다

- 메모리의 데이터와 디스크 백업은 **전체 그대로**, 브라우저에 저장하는 직전(`partialize`)에만 줄인다.
- 사용자가 고치지 않아 **기본값과 같은** 시나리오는 저장하지 않는다. 불러올 때 `normalizeCaseRemodeling`이 빠진 단계를 기본 카탈로그로 다시 채운다. 하나라도 고친 단계는 통째로 저장한다.
- **비교 기준**은 「새 기본 시나리오를 불러올 때와 똑같이 정리(normalize)까지 거친 것」이다. 저장된 시나리오는 모두 정리를 거친 모양이라 정리 전 기본값과는 항상 다르게 보인다(처음에는 0/108로 일치해 이를 발견).
- **채우는 쪽**도 정리까지 거친 기본값을 쓴다(정리 전 값으로 채우면 월세 상승분이 달라져 36건 모두 달라졌음 → 수정).
- 물건 객체는 불변 갱신이라 같은 객체는 비교 결과를 재사용(WeakMap)해 저장마다 다시 비교하지 않는다.

권리분석 원문 글자는 화면 PDF가 문서로 저장된 경우에만 글자 사본을 생략한다(PDF를 못 받았으면 글자 사본이 유일한 전문이라 남김). 이미 저장된 값은 건드리지 않는다.

## 4. 결과 (실제 데이터)

| | 이전 | 이후 |
|---|---|---|
| 38건 저장 크기 | 약 550만 자 | 약 205만 자 (**약 63% 감소**) |
| 물건당 | 약 15만 자 | 약 5.4만 자 |
| 브라우저 저장 용량 | 약 100% | 39.2% |
| 저장 가능 물건 수 | 약 38건 | 약 90건 |

## 5. 왕복 검증

- 36건: 저장용으로 줄임 → 직렬화 → 불러오기(정리) 후 **내용 36/36 동일**, 다시 저장해도 **크기 동일**
- 기본값과 같은 시나리오 108/108 인식, 한 단계만 고치면 그 단계만 저장되고 복원 시 다른 단계도 원래와 동일
- 실제 앱: 빈 브라우저에 36~38건 복구 → 새로고침 → 리모델링 화면(시나리오·비용)이 정상으로 다시 채워짐

## 6. 사용률 표시

데이터 화면에 사용률 막대(물건 데이터·사이트 전체 localStorage), 80%를 넘으면 상단 경고(95% 이상은 빨간색). 20초마다 문자열 길이만 읽어 가볍다.

## 7. 알려진 한계와 다음 단계

- 카탈로그 비용줄은 원래부터 불러올 때 가격을 카탈로그 값으로 다시 채우고 선택(selected)만 유지한다(이번 변경과 무관한 기존 동작).
- 체크리스트 중복(약 9%)은 모델 변경이 커서 제외.
- **2단계**: 저장 위치를 IndexedDB(물건별 레코드)로 이전 → 용량 사실상 무제한, 바뀐 물건만 저장. 기존 데이터는 확인 전까지 원본 유지.
- **3단계(선택)**: 디스크를 기준 저장소로 하고 브라우저는 캐시로 → 주소·포트·브라우저가 바뀌어도 데이터가 갈라지지 않음.
