# 데이터 보호 설계 — 디스크 백업 · 저장 보호 장치 · 복구

> 기준일: 2026-10-25 · 구현: `src/lib/backup/`, `src/app/api/backup/`, `src/components/disk-recovery-banner.tsx`, `backup-panel.tsx`

## 1. 문제

물건 목록이 사라지는 일이 반복됐고, 그때마다 백업도 남아 있지 않았다. 구조적 약점은 두 가지였다.

- **백업이 데이터와 같은 곳**: 물건 데이터는 브라우저 localStorage, 백업은 같은 브라우저의 IndexedDB에 있었다. 사이트 데이터 삭제·포트/주소 변경·브라우저 교체가 일어나면 둘이 함께 사라진다.
- **주소·포트마다 저장소가 따로**: `localhost:3000`, `localhost:3001`, 배포 도메인은 서로 다른 저장소다. 주소가 바뀌면 목록이 없어 보인다.

## 2. 설계 원칙

1. 백업은 **브라우저 밖**(이 컴퓨터의 파일)에 둔다.
2. 같은 내용은 다시 쓰지 않고, 물건이 0건인 데이터는 저장하지 않는다(빈 목록이 정상 백업을 밀어내지 못하게).
3. 물건이 **가장 많았던 시점**은 정리 규칙에서 제외해 항상 남긴다.
4. 되돌리기 어려운 작업 직전에는 디스크 저장이 끝난 뒤에 진행한다.
5. 읽기 실패·급감 같은 위험 신호에서는 원본을 먼저 보존한다.

## 3. 구성

| 구성요소 | 역할 |
|---|---|
| `disk-store.ts` (서버) | `private/backups/`에 gzip 저장, 목록·읽기, 정리. 임시 파일에 쓴 뒤 이름을 바꿔 쓰는 도중 중단돼도 깨진 파일이 남지 않음 |
| `/api/backup` | `POST` 저장, `GET` 목록·내용. **localhost에서만** 동작(다른 PC는 403, 배포 서버는 501) |
| `disk-client.ts` | 브라우저에서 호출, 마지막 성공·오류 상태 기록 |
| `auto-backup.tsx` | 앱을 열고 2초 뒤, 데이터가 바뀌고 15초 뒤 저장 |
| `backup-store.ts` | 기존 브라우저 백업(IndexedDB)과 `backupBefore`(디스크 저장 완료까지 최대 8초 대기 후 작업 진행) |
| `persist-guard.ts` | 저장 보호 장치(아래 5절) |
| `disk-recovery-banner.tsx` | 시작할 때 복구를 권하는 배너 |
| `backup-panel.tsx` | 데이터 화면 맨 위 「백업·복구」: 디스크 백업 목록, 병합/교체 복구, 파일로 저장 |

## 4. 저장 규칙

- **파일 이름**: `YYYYMMDDTHHMMSSZ_<건수>c_<사유>.json.gz` (예: `20261025T071637Z_36c_앱-열-때.json.gz`)
- **중복 제외**: 데이터의 SHA-1이 마지막 백업과 같으면 건너뜀(삭제 직전·수동 백업은 `force`로 항상 저장)
- **최다 시점**: `peak.json.gz`(+`peak.meta.json`). 물건 수가 지금까지의 최대와 같거나 많을 때 갱신, 정리에서 제외
- **정리**: 최신 40개 + 최근 48시간은 시간별 1개 + 최근 90일은 하루 1개. 만든 지 10분 이내 파일은 지우지 않음
- **저장 시점**: 앱 열 때 · 변경 후 15초(디바운스) · 삭제/갱신/복원/새로 시작 직전 · 수동 「지금 디스크 백업」

## 5. 저장 보호 장치 (`persist-guard.ts`)

데이터가 조용히 사라지는 두 경로를 막는다.

1. **불러오기 실패**: 저장된 데이터를 해석하다 오류가 나면, 빈 기본값으로 시작한 뒤 그 빈 상태가 저장돼 원본을 덮어쓴다. → 원본을 디스크에 `읽기 실패 원본`으로 보존하고, 사용자가 확인하기 전까지 브라우저 저장을 멈추고 빨간 안내를 띄운다.
2. **물건 급감**: 물건이 3건 이상 있다가 절반 아래로 줄어드는 저장이 들어오면, 덮어쓰기 직전의 원본을 디스크에 `급감 전 원본`으로 먼저 남긴다.

> **중요한 예외**: 저장된 값이 **아예 없는** 경우(처음 여는 브라우저·다른 포트)는 오류가 아니다. 이 경우에는 기본값으로 시작하고 저장을 막지 않는다. (초기 구현이 이 경우를 오류로 오판해 저장을 막는 버그가 있었고, 같은 날 수정했다 — DEVLOG 참고)

## 6. 복구 배너

시작할 때 디스크 백업 중 물건 수가 많은 것부터 최대 3개를 살펴, **현재 목록에 없는 물건**이 눈에 띄게 많으면 알린다.

- 조건: 현재 목록이 0건이거나, (없는 물건 ≥ 3건 이고 현재 목록 < 백업의 60%)
- 동작: 「없는 물건 N건 복구(병합)」 — 같은 id의 물건은 건드리지 않고 없는 물건만 추가. 복구 직전 현재 상태도 백업
- 「이 백업은 다시 묻지 않기」는 백업 파일 이름 단위로 기억. 「새로 시작」 이후에는 그 시각 이전 백업을 제안하지 않음(예전 데이터가 되살아나지 않게)

## 7. 「처음부터 새로 시작」

지우기 직전의 물건 데이터를 디스크에 `새로 시작 직전`으로 먼저 저장하고, 저장이 실패하면 **지우지 않고 멈춘다**. 디스크 백업 폴더는 지우지 않는다(브라우저 안의 백업만 지움).

## 8. 한계

- 복사본이 **한 곳**(프로젝트가 있는 외장 SSD)이다. 시간 백업 미설정 → 내부 디스크에 한 부 더 두는 것을 다음 작업으로 계획.
- 개발 서버가 떠 있어야 저장된다. 드라이브 연결이 끊기면 저장이 실패하고 백업·복구 화면에 오류가 표시된다.
- 사진·PDF 파일(IndexedDB)과 서버 수집 원본은 백업에 포함되지 않는다(「다시 수집」으로 복구).

## 9. 검증

- 임시 폴더에서 저장·같은 내용 건너뜀·강제 저장·빈 데이터 거부·persist 래퍼 형식·깨진 JSON 거부·최다 시점 보존·경로 이탈 시도 차단을 확인.
- 실제 사용 중인 브라우저가 열자마자 디스크 백업을 만들고 최다 시점 파일이 갱신되는 것을 확인.
- 빈 저장소의 브라우저에서 복구 배너가 뜨고, 「복구(병합)」으로 36건이 저장되는 것까지 확인(저장이 막히던 버그 수정 뒤).
