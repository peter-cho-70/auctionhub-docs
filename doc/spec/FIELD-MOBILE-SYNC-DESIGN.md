# ⭐ 임장 모바일 연동 방법론 (Field Pack / 현장 입력 → 로컬 반영)

> ⭐ **해야 할 일** — 방법론만 정리했고 구현은 시작 전이다. 다음 순서: 아래 9장의 결정 3가지 → 8장 단계 0·1(임장 팩 만들기 + 폰 읽기 전용 보기).
> 기준일: 2026-10-29 · 상태: **방법론 초안(구현 없음)** · 폰: Android(Chrome) · 앱은 배포하지 않고 Mac 로컬에서만 사용
> 목적: 임장 나가는 물건의 정보를 폰에서 보고, 수정하고, 신규로 입력한 뒤, 그 결과를 Mac의 로컬 데이터에 안전하게 합친다.

## 결론 (3줄)

1. **원본은 항상 Mac**이다. 폰은 「작업 사본」만 갖고, 현장에서 바뀐 내용은 **변경 묶음(change set)** 으로 돌려보내 Mac에서 **미리 보고 확인한 뒤** 합친다(덮어쓰기·삭제 없음).
2. 연결은 **두 통로를 함께** 쓴다. **통로 A(파일)** 는 신호가 없어도 되는 기본 통로이고, **통로 B(Tailscale)** 는 폰을 앱처럼 설치(PWA)하고 신호가 될 때 자동으로 맞추는 보조 통로다. 둘 다 같은 「임장 팩 / 변경 묶음」 형식을 쓴다.
3. 클라우드(Supabase·구글 드라이브 등)는 쓰지 않는다. 세입자 이름·전화·현관 비밀번호가 들어 있어 **외부 서버를 거치지 않는** 방식만 고른다.

## 1. 지금 구조에서 알아야 할 제약

| 사실 | 의미 |
| --- | --- |
| 물건 데이터는 서버가 아니라 **브라우저 IndexedDB**(`auctionflow-app`)에 있다 | 폰 브라우저는 **다른 저장소**라 데이터가 비어 있다. 폰이 `:3000`에 접속만 해서는 물건이 보이지 않는다 |
| 서버(`hub`, 포트 3000)는 Mac 안에서 도는 운영 모드이고, 같은 Wi-Fi 주소(`192.168.x.x:3000`)로도 화면이 열린다 | 화면은 열리지만 데이터가 없다. 서버 쪽 API 중 `backup`·`pinned/upload`는 Host가 localhost가 아니면 403으로 막혀 있다 |
| 사진·PDF는 별도 IndexedDB(`taein-media`, `field-photo`)와 `private/` 폴더에 있다 | 사진은 용량이 커서 팩에서 따로 다뤄야 한다 |
| 「JSON 전체 보내기」는 **삭제된 기능이며 되살리지 않는다**(프로젝트 규칙) | 전체 내보내기가 아니라 **임장 물건만 잘라 낸 팩**을 새로 만든다 |
| 되돌리기 어려운 작업은 `backupBefore(...)` + 사용자 확인 후에만 | Mac에서 결과를 합칠 때도 같은 규칙을 따른다 |
| 같은 물건 병합 로직(`mergeSameCasePreservingLocalAnalysis`)이 이미 있다(클라우드 병합용) | 「이미 있는 값은 지키고 비어 있는 곳을 채운다」는 원칙을 참고하되, 현장 입력은 **필드 단위**로 새로 설계한다 |

## 2. 전체 흐름

```
[Mac] 임장 갈 물건 고르기 → 「임장 팩」 만들기
        │  (통로 A: 파일)            (통로 B: Tailscale)
        ▼                              ▼
[폰] 팩 열기 · 오프라인 저장 ──── 현장에서 보기 · 수정 · 신규 입력 ────┐
        │                                                             │
        ▼ 변경 묶음 내보내기(파일) / 신호 되면 자동 전송(B)            │
[Mac] 「임장 결과 가져오기」: 변경 내용 미리 보기 → 충돌 해결 → 백업 → 적용
```

## 3. 임장 팩 (Mac → 폰)

- **대상**: 임장 후보로 등록한 물건 중 사용자가 고른 것만(보통 3~10건). 전체 데이터는 보내지 않는다.
- **담는 것(물건마다 필요한 조각만)**
  - 읽기 전용: 주소·사건번호·입찰일·요약, 권리분석 요약(대항력·인수액·임차권등기), 스크리닝 신호, 주변 시세 스냅샷, 지역정보
  - **수정 가능**: 임차인 기록(확인 이름·전화·성향·연장·확인 월세/보증금·메모), 호실 표(룸 형태·면적·메모)와 호실 현장 점검(전기·가스·수도·우편물·판단·현관 비밀번호), 관리업체·주변 부동산 연락처·친절도, 임장 메모
- **담지 않는 것**: 감정평가서·등기부 PDF 등 원문 문서, 다른 물건, 설정값
- **형식**: `*.afpack.json`(JSON, 선택적으로 비밀번호 암호화) + 사진은 압축본을 같은 묶음에 포함. 팩 머리말에 `packId`, 만든 시각, 물건별 **기준 버전**(해당 조각의 `updatedAt` 해시)을 적어 나중에 충돌을 알아낸다.
- **현관 비밀번호**: 현장에서 쓰려면 폰에 있어야 한다. 팩 만들 때 **「비밀번호 포함」 체크(기본 꺼짐)** 로 정하고, 포함하면 **팩 암호화를 강하게 권장**한다(분실 대비).

## 4. 폰 앱 (현장용)

- **형태**: 같은 Next 앱 안의 모바일 전용 경로(`/field`)를 **PWA**로 만든다. 타입·정규화 함수를 그대로 재사용하되, 화면은 데스크톱 표가 아니라 **물건 → 층/호실 → 세입자 카드** 순의 한 손 조작용으로 따로 만든다. (확인 필요: 기존 컴포넌트 재사용 범위 vs 모바일 전용 화면 비용)
- **오프라인**: 팩을 폰 IndexedDB에 저장하고 서비스 워커로 앱 껍데기를 캐시해 **신호 없이도** 열고 입력한다.
- **화면 범위(합의된 4가지)**
  1. 세입자 정보 — 면담 카드와 같은 입력 항목, 세입자 추가
  2. 호실 현장 점검 — 공실 확인 신호, 현관 비밀번호, 호실 룸 형태·면적·메모, 호실 추가
  3. 관리업체·부동산 — 상호·전화·상담사 친절도, 부동산 연락처·시세 의견
  4. 사진·신규 물건 — 호실/건물 사진 촬영, 임장 중 새 물건(주소·메모) 임시 등록
- **로컬 변경 기록**: 폰에서의 모든 수정은 원본을 바꾸지 않고 **변경 기록(op log)** 으로 쌓는다. 한 건은 `{물건, 대상 종류, 대상 id, 필드, 새 값, 시각, 기기 id}` 이다. 새 항목(세입자·호실·연락처·물건)은 폰에서 **UUID를 직접 만들어** Mac의 id와 겹치지 않게 한다.
- **자동 판단은 제안만**: 공실 의심 같은 계산은 폰에서도 같은 규칙으로 보여 주되, 확정은 사람이 한다(기존 원칙).

## 5. 변경 묶음 (폰 → Mac)

- **형식**: `*.afchanges.json` — 변경 기록 + 새 항목 + 사진 파일 참조.
- **Mac의 「임장 결과 가져오기」**
  1. 파일을 올리거나(통로 A) 서버가 받아 둔 묶음을 불러온다(통로 B).
  2. **미리 보기**: 물건별로 「세입자 3명 수정, 호실 2곳 점검, 연락처 1건 추가, 사진 6장」처럼 보여 주고 항목별 체크.
  3. **충돌 검사**: 팩을 만든 뒤 Mac에서 같은 필드가 바뀌었으면(기준 버전이 다름) 「Mac 값 / 폰 값」을 나란히 보여 주고 사용자가 고른다. 기본값은 **Mac 값 유지**.
  4. `backupBefore("임장 결과 가져오기")` 후 필드 단위로 적용. 사진은 `field-photo` 저장소에 넣고 디스크 사본도 만든다.
- **규칙**
  - **삭제는 동기화하지 않는다**(폰에서 지운 것은 「삭제 요청」으로 표시만, Mac에서 직접 확인). 데이터 보호 원칙과 맞춘다.
  - 같은 변경 묶음을 두 번 가져와도 결과가 같다(`packId`·변경 id로 중복 방지).
  - 폰에서 만든 신규 물건은 **「임장 중 신규(초안)」** 로 들어오고, Mac에서 주소 확정·태인/대법원 정보 보강을 마쳐야 일반 물건이 된다.
  - 가져오기가 끝나면 폰에 **「반영 완료」 표시**를 보내고(파일/통로 B), 완료된 팩은 폰에서 지우도록 권한다.

## 6. 두 통로

| | 통로 A: 파일 | 통로 B: Tailscale(VPN) |
| --- | --- | --- |
| 역할 | 기본·비상 통로. 신호 없어도 됨 | 폰 앱 설치(PWA)와 자동 동기화 |
| 필요한 것 | 파일을 옮길 방법 | Mac과 폰에 Tailscale, Mac이 켜져 있고 서버가 실행 중 |
| 현장(LTE/무신호) | 팩을 미리 넣어 두면 문제없음 | 신호가 있을 때만 동기화(편집은 오프라인 가능) |
| 외부 유출 | 없음(옮기는 방법에 따라 다름) | 없음(전용 사설망, 중간 서버에 데이터 저장 안 함) |
| 약점 | 사람이 파일을 옮겨야 함 | 설정·유지 필요, Mac 전원/절전 영향 |

### 통로 A: Android ↔ Mac 파일 옮기는 방법 (AirDrop 불가)
- **USB 케이블**(파일 전송 앱 필요): 가장 단순하고 인터넷을 거치지 않는다.
- **Tailscale Taildrop**: 같은 Tailscale 망 안에서 Android↔Mac 파일 전송. 클라우드를 거치지 않는다. (확인 필요: 실제 기기에서 속도·편의)
- **Syncthing**(P2P 동기화 폴더): 한 번 설정하면 자동. (확인 필요: Android 백그라운드 제한)
- **피하는 방법**: 구글 드라이브·카카오톡 나에게 보내기 등 **외부 서버를 거치는 방법**(세입자 개인정보가 포함되므로 비권장).

### 통로 B: Tailscale 구성
- Android Chrome은 **HTTPS(보안 컨텍스트)** 여야 서비스 워커·홈 화면 설치가 된다. 일반 `http://192.168.x.x`는 안 된다. Tailscale의 HTTPS 인증서(MagicDNS `*.ts.net`)를 쓰면 **설치 가능한 PWA**가 된다. (확인 필요: `tailscale serve` 설정과 인증서 발급 절차)
- 서버는 `127.0.0.1`에서만 받고 Tailscale이 그 앞에서 HTTPS로 중계하는 구성을 권장한다(Wi-Fi의 다른 기기에서 직접 접근 차단).
- 동기화 API(`/api/field-sync`)는 **공유 비밀 토큰**과 **허용 기기**를 확인한다. 기존 `backup`의 localhost 전용 검사는 그대로 두고, 동기화 API만 별도 규칙을 둔다.
- 서버에 받아 둔 변경 묶음은 `private/field-inbox/`(gitignore)에만 두고, 사용자가 Mac에서 가져오기를 확인한 뒤에 반영한다. **서버가 받는 즉시 데이터에 쓰지 않는다.**

## 7. 개인정보·보안

- 세입자 이름·전화·확인 월세·현관 비밀번호가 폰에 저장된다 → **폰 화면 잠금 필수**, 팩 **암호화(AES-GCM, 비밀번호는 사용자가 정함)** 권장, **보관 기간**(예: 반영 후 7일)이 지나면 앱이 지우도록 알린다.
- 비밀번호 칸은 폰에서도 가려서 표시하고, 화면 PDF·인쇄물·내보내기에는 넣지 않는다(기존 규칙 유지).
- 통로 B의 토큰은 코드/저장소에 넣지 않고 `.env`에만 둔다.
- 공개 저장소·배포는 하지 않는다. `private/field-inbox/`, `private/field-packs/`는 gitignore 대상이다.

## 8. 단계별 계획

| 단계 | 내용 | 확인 방법 |
| --- | --- | --- |
| 0 | 결정: 파일 옮기는 방법(USB/Taildrop/Syncthing), Tailscale 설치, 서버 바인딩 확인 | 폰↔Mac으로 테스트 파일 1건 옮기기 |
| 1 | **임장 팩 만들기**(Mac) + **폰 읽기 전용 보기**(오프라인) | 비행기 모드에서 물건·세입자·호실이 열림 |
| 2 | **폰 편집 + 변경 묶음 내보내기**, Mac **가져오기(미리 보기·충돌·백업)** — 세입자·호실 점검·연락처 | 가짜 데이터로 팩→수정→가져오기 왕복이 같은 결과, 두 번 가져와도 중복 없음 |
| 3 | **사진**(촬영·압축·가져오기), **신규 물건 초안** | 사진 용량·저장 확인, 초안이 일반 물건으로 승격되는지 |
| 4 | **통로 B**: PWA 설치, 서비스 워커, 자동 전송, 충돌 화면 | 신호 꺼짐/켜짐 전환, Mac 절전 시 동작 |
| 5 | 팩 암호화, 보관 기간, 반영 완료 표시 | 분실 시나리오 점검 |

각 단계는 **실제 개인 데이터가 아니라 합성 데이터로 먼저 시험**하고, 단계가 끝날 때마다 `backupBefore`·충돌·중복 방지를 다시 점검한다.

## 9. 열린 질문 / 확인 필요

1. 폰↔Mac 파일 전송은 어느 방법으로 할지(USB / Taildrop / Syncthing).
2. 팩에 **현관 비밀번호를 기본 포함할지**(편의 vs 분실 위험). 제안: 기본 제외 + 호실별 선택 포함.
3. 모바일 화면을 기존 컴포넌트 재사용으로 할지, **모바일 전용 화면**으로 새로 만들지(제안: 전용 화면, 타입·정규화·병합 규칙만 공유).
4. 임장 중 신규 물건에 필요한 최소 입력 항목(주소, 사건번호 또는 메모, 사진).
5. 태인·대법원 조회는 **Mac에서만** 한다(IP 차단 위험 때문에 폰에서 직접 접속하지 않는다) — 그대로 유지해도 되는지.
6. 같은 물건을 여러 번 임장할 때 팩을 매번 새로 만들지, 이전 팩에 이어 갱신할지.
7. Mac이 절전일 때 통로 B를 어떻게 할지(절전 방지 설정 vs 통로 A로 대체).

## 10. 하지 않는 것 (이번 범위 밖)

- 클라우드(Supabase 등) 동기화, 앱 배포, 다중 사용자 동시 편집
- 폰에서의 태인·대법원 직접 조회, 원문 PDF 열람
- 삭제 동기화, 자동 병합(사람 확인 없는 반영)
