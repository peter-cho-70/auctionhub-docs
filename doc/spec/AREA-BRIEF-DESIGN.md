# 주변 소개(Area Brief) 설계 — 주소 말풍선

> 기준일: 2026-10-28 · 상태: **1단계 구현·시험 완료**(`src/lib/area-brief/`, 시험 `scripts/region-research/area-brief-try.mjs`), 2단계부터 미구현 · 구현 예정 위치: `src/lib/area-brief/`, `src/app/api/area-brief/`, `src/components/address-tip.tsx`

## 1. 목적

물건 주소를 기준으로 주변시설·아파트·도로·시세 기본 자료를 미리 조사해 짧은 소개글로 만들고, 주소에 마우스를 올리면 말풍선으로 보여 준다. 내용은 기준일과 출처를 달아 지속적으로 갱신한다. 입찰 판단의 **참고 자료**이며 점수·스크리닝 판정에는 쓰지 않는다.

## 2. 원칙

1. **확인된 숫자만 글에 쓴다.** 자료가 없는 항목은 「조사 전」, 추정은 「추정」으로 구분한다. 글 생성 모델이 사실을 새로 만들어 내지 못하게, 모델에는 수집된 자료만 넘기고 그 밖의 내용은 쓰지 말라고 지시한다.
2. **키 없이 시작한다.** 외부 키가 필요한 자료원(카카오 로컬, 브이월드, 아파트 매매 API)은 나중에 같은 자리에 끼워 넣을 수 있게 자료원을 교체 가능한 구조로 둔다.
3. **로컬 우선.** 조사 결과는 물건 데이터(`AuctionCase`)에 저장돼 디스크 백업에 포함된다. 외부 서비스로 나가는 정보는 **좌표(위도·경도)와 시군구·동 이름**뿐이고, 소유자·임차인 같은 개인정보는 보내지 않는다.
4. 사용자 데이터(물건)를 지우거나 덮어쓰지 않는다. 갱신은 `areaBrief` 필드만 바꾼다.

## 3. 자료원 (키 없이 가능한 범위)

2026-10-27에 대전 서구 용문동 좌표로 직접 시험한 결과를 적는다.

| 항목 | 자료원 | 시험 결과 | 한계 |
|---|---|---|---|
| 좌표 | 기존 지오코딩(`geocode-server`, 행안부·네이버) / 물건에 저장된 `nearbyMarketAnalysis.lat/lng` | 사용 중 | 좌표 없으면 조사 불가 → 「위치 없음」 |
| 주변시설(학교·마트·편의점·은행·병원·약국·지하철역) | OpenStreetMap Overpass API(키 없음, **사용자 에이전트 지정 필수**) | 반경 600m에서 학교 6, 슈퍼마켓 7, 은행 2, 편의점 1 확인 | **지하철역이 빠졌다**(실제로 가까운 역이 있어도 0건). 편의점·병원·약국은 누락이 많다. 개수는 「최소 N곳」으로 표현 |
| 도로 | Overpass `highway` 태그 | 반경 300m에서 도로 약 58개, 이 중 폭·차로 정보가 있는 것은 **4개뿐** | **도로폭은 거의 알 수 없다.** 소개글에는 도로 등급(간선·보조간선·이면)만 쓰고 폭은 「임장 때 확인」, 직접 입력 칸 제공 |
| 주변 다가구·연립 시세 | 기존 `nearbyMarketAnalysis`(국토부 실거래 다가구·연립) | 사용 중 | 아파트는 아님 |
| 주변 아파트 | 국토부 아파트 매매 API | **키 미등록**(활용신청 필요) | 신청 전까지 「조사 전」. 시설 자료에서 아파트 단지명만 보조로 가져올 수 있으나 시세는 없음 |
| 임대 수요 | `src/lib/region/daejeon-rent-demand.json`(동별) | 사용 중(대전만) | 세종은 자료 없음 |

나중에 키를 넣을 자리: 카카오 로컬(시설 정확도↑), 브이월드 도로구간(도로폭), 아파트 매매 API(주변 아파트 시세).

## 4. 데이터 모델

`AuctionCase.areaBrief?: AreaBrief | null` (선택 필드 → 기존 데이터·마이그레이션 영향 없음)

```ts
interface AreaBrief {
  schemaVersion: 1;
  /** 마지막 조사 시각(ISO). 말풍선에 기준일로 표시 */
  surveyedAt: string;
  /** 조사에 쓴 좌표와 반경(m) */
  origin: { lat: number; lng: number; radiusM: number };
  facilities: Array<{ kind: "school" | "mart" | "convenience" | "bank" | "hospital" | "pharmacy" | "station"; count: number; nearest?: { name: string; distanceM: number } }>;
  roads: { dominantClass: string | null; widthM: number | null; widthSource: "osm" | "manual" | null; note: string };
  market: { rentDemand?: {...}; nearbySummary?: string } | null; // 기존 자료 재사용
  apartments: { status: "unsurveyed" | "partial" | "ok"; names: string[] };
  /** 사람이 읽는 소개글(2~4문장)과 한 줄 요약 */
  summary: string;
  headline: string;
  /** 출처별 상태: 성공/실패/조사 전 + 메시지 */
  sources: Array<{ id: string; label: string; status: "ok" | "failed" | "skipped"; at: string; message?: string }>;
  /** 직전 조사와 달라진 점(없으면 빈 배열) */
  changes: string[];
}
```

도로폭을 사용자가 직접 입력하면 `widthSource: "manual"`로 기록하고, 자동 갱신이 이 값을 덮어쓰지 않는다.

## 5. 조사·갱신 흐름

1. **조사**: `POST /api/area-brief` (`caseId` 대신 좌표·동 이름을 받는다) → 서버가 Overpass에서 시설·도로를 한 번에 조회 → 정리된 자료 반환. 서버 쪽에서 결과를 `private/area-brief-cache/`에 좌표(소수 3자리) 단위로 24시간 캐시해 같은 동네의 연속 조회를 줄인다.
2. **글 생성**: 정리된 자료만으로 소개글을 만든다. 1차는 **규칙 기반 문장 조립**(키·비용 없음, 환각 없음), 2차 선택 기능으로 Gemini 문체 다듬기(자료에 없는 사실 추가 금지, 숫자 보존 검증 후 어긋나면 규칙 기반 문장으로 되돌림).
3. **저장**: `updateCase(id, { areaBrief })`. 이전 값과 비교해 `changes`를 채운다(예: 「슈퍼마켓 7→8곳」).
4. **갱신 시점**: 기준일이 30일 지난 물건은 앱이 열릴 때 **목록 순서대로 천천히**(요청 간 1.5초, 동시 1건) 다시 조사한다. 상세 화면의 「주변 다시 조사」 버튼으로 즉시 갱신. 외부 서비스 부하를 줄이려고 한 번에 5건까지만 자동 갱신하고 나머지는 다음 접속에 이어서 한다.
5. 실패하면 이전 내용을 그대로 두고 `sources`에 실패를 남긴다. 조사 중 저장이 한도를 넘는 상황에 대비해 `areaBrief`는 용량이 작게(수 KB) 유지한다.

## 6. 화면

- **`AddressTip`** 컴포넌트: 주소 텍스트를 감싸 마우스를 올리면(키보드 포커스도 지원) 말풍선을 연다. 말풍선 구성: 한 줄 요약 → 소개글 → 시설 개수 표 → 도로 → 시세 → 기준일·출처·「다시 조사」 링크. 조사 전이면 「아직 조사 전입니다 · 지금 조사」 버튼.
- 적용 위치: 물건 목록 행, 물건 상세 제목 아래 주소, 임장 후보 카드, 지도·동선 패널, 오늘의 추천 패널.
- 모바일/터치: 호버가 없으므로 주소를 누르면 같은 말풍선이 열린다.
- 상세 화면에는 말풍선 내용을 펼쳐 둔 「주변 소개」 섹션을 둔다(도로폭 직접 입력 칸 포함).

## 7. 개인정보·외부 호출

- 외부로 나가는 것: 좌표, 시군구·동 이름. 사건번호·소유자·채권자·임차인·금액은 보내지 않는다.
- OpenStreetMap Overpass는 공용 서버이므로 요청 간격과 캐시를 지키고, 앱 이름이 들어간 사용자 에이전트를 지정한다.
- `private/area-brief-cache/`는 `private/`라 저장소에 올라가지 않는다.

## 8. 구현 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| 1 | Overpass 조회·정리(`fetch-overpass.ts`), 규칙 기반 소개글(`compose.ts`), 단위 테스트(고정 응답으로 문장 확인) | 대전·세종 실제 물건 3건으로 결과 확인 |

| 3 | `AddressTip` + 상세 「주변 소개」 섹션, 목록·임장·추천 패널 적용 | 화면 확인(호버·키보드·모바일) |

| 5 | (선택) Gemini 문체 다듬기, 키 도입 시 자료원 교체 | 숫자 보존 검증 |

## 8-1. 1단계 시험 결과 (2026-10-28)

- 대전 서구 용문동·탄방동, 유성구 전민동의 **동 중심 좌표**로 조회했다. 용문동은 용문역 225m, 학교 1·마트 7·은행 3·병원 8, 주간선도로(계룡로)가 나왔고, 탄방동은 탄방역 590m·학교 4·마트 8·병원 17이 나왔다. 전민동은 역·마트가 0으로 나왔다(실제로 없는지 지도 자료 누락인지 구분하지 못한다).
- 지하철역은 `railway=station`과 `station=subway` 태그를 함께 조회하니 잡혔다(1000m). 이름 없는 출입구는 버린다.
- **도로 폭 정보는 3곳 모두 0건**이라 소개글은 「임장에서 확인 필요」로 쓴다.
- 물건에 저장된 좌표는 대부분 **동 중심**(`precision: dong`)이라, 소개글 끝에 위치 차이 안내 문구를 붙인다. 지번 단위 좌표(네이버 지오코딩 키)가 있으면 정확도가 오른다.
- 공용 Overpass 서버는 바쁠 때 502를 돌려준다. 서버를 번갈아 가며 2·4·8초 간격으로 다시 시도하도록 했다.

## 9. 확인 필요 / 열린 질문

- OSM의 지하철역 누락 원인(좌표·태그 구조)을 조사해 보완할 수 있는지 1단계에서 확인한다. 보완이 안 되면 역 정보는 「조사 전」으로 두고 카카오 키 도입 후 채운다.
- 반경: 시설 600m(도보 10분 안팎), 도로 300m를 기본으로 하고 조정 가능하게 한다.
- 세종은 아파트 중심이라 시설 항목 외에 주변 아파트 시세가 핵심인데, 아파트 매매 API 신청 전에는 비어 있다.
- 소개글 문체·분량(현재 2~4문장)은 1단계 결과를 보고 같이 정한다.
