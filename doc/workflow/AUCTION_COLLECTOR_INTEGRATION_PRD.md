# 경매자료 수집기 통합 PRD — "다가구경매파이프라인" → AuctionFlow Pro

> 작성일: 2026-10-24 / 작성: Claude · 상태: **사전 검토 완료, 구현 전**
> 관련 외부 프로젝트: `다가구경매파이프라인` (로컬 전용, 이 저장소와 별도)
> 문서 사이트: https://peter-cho-70.github.io/dagagu-auction-docs/

## 1. 배경

대전 다가구주택 경매 물건을 조사하는 과정(① 대법원 법원경매정보에서 1차 리스트업 → ② 전문 경매사이트에서 상세 자료 확보 → ③ 권리분석)을 자동화하기 위해 별도 로컬 프로젝트(`다가구경매파이프라인`)를 먼저 만들었다. ego-lite 브라우저(`ego-browser nodejs`)로 실제 브라우저를 조작해:

1. 대전 다가구주택 경매 물건 전체(신건+유찰)를 법원경매정보에서 긁어오고
2. 로컬 웹앱(지도·즐겨찾기·정렬)에서 물건을 고르면
3. 보스옥션(대장옥션)에 접속해 감정평가서·매각물건명세서·현황조사서·문건/송달내역·등기(건물)·등기(토지) 6종 문서를 가져와 로컬에 저장한다

(코드: 별도 저장소. 로컬 경로 `/Volumes/data/vibecoding/egolite/다가구경매파이프라인`. 전체 설계는 위 문서 사이트의 PRD 참고.)

작업 중 이 저장소(AuctionFlow Pro)를 다시 보니, **물건 관리·PDF 자동분석·세입자분석·시세분석**이 이미 훨씬 성숙하게 구현되어 있었다. 특히 `CaseSourceDocumentKind`에 **`daejangauction-pdf`라는 이름으로 대장옥션(보스옥션)이 이미 1급 지원 대상**으로 들어가 있다(`src/lib/pdf/daejang-auction-pdf-parser.ts`). 두 프로젝트를 하나의 코드베이스로 합치기보다는, **"수집"은 다가구경매파이프라인(로컬 전용)이, "관리·분석"은 AuctionFlow Pro가** 맡고 둘을 연결하는 편이 합리적이라고 판단했다 — ego-browser는 사람의 로그인 핸드오프가 필요한 로컬 전용 도구라 Vercel 서버리스 배포본과는 애초에 합쳐질 수 없다.

이 문서는 그 연결을 실제로 구현하기 **전에** 핵심 가정을 검증하고 설계를 정리한 사전 작업 결과물이다.

## 2. 이 저장소(AuctionFlow Pro)의 기존 자산 — 재사용 가능한 것

| 자산 | 위치 | 비고 |
|---|---|---|
| 사건 생성 API | `POST /api/pdf-to-case` | PDF 업로드 → 텍스트 추출 → 구조화 → `newCaseInput` 반환 |
| 구조화 API | `POST /api/pdf-to-json` | 사건 생성 없이 구조화 JSON만 |
| 대장옥션 전용 파서 | `src/lib/pdf/daejang-auction-pdf-parser.ts`, `daejang-auction-structured.ts` | 물건 요약 페이지(입찰진행·임차인현황·등기부현황 요약) 포맷 전용 |
| 등기부 파서 | `auctionone-structured.ts`의 `parseRegistryRights` (`registry-building`/`registry-land`) | 법원·등기소 표준 포맷 기준으로 보임(사이트 종속 아님) |
| 매각물건명세서 파서 | 같은 파일의 `parseTenants` (`tenant-report`) | `stored-pdf-name.ts`에 "매각물건명세서"로 매핑됨 |

## 3. 오늘 실제로 검증한 것 (추측 아님 — 직접 실행·확인)

### ✅ 확인됨 — 개별 문서 팝업은 텍스트 추출이 안정적이다
`다가구경매파이프라인`이 이미 보스옥션의 매각물건명세서·현황조사서·등기(건물)·등기(토지)·문건송달내역을 열람할 때, 실제 내용이 최상위 문서가 아니라 같은 출처 iframe(`pop_view*_ifm.html`) 안에 있다는 걸 발견하고 `contentDocument`로 들어가 전체 텍스트를 정상적으로 뽑아내는 데 성공했다(2026타경600076 기준 등기부 건물 3,964자, 토지 3,714자 등 — 표·숫자 누락 없이 온전함). 이 문서들은 보스옥션이 자체 제작한 화면이 아니라 **법원·등기소가 발급한 원본 PDF를 그대로 띄우는 뷰어**다(워터마크 "개인정보유출주의", "등기사항전부증명서(말소사항 포함)" 등 공식 양식 확인).

→ 이 저장소의 `registry-building`/`registry-land`/`tenant-report`/`appraisal-report` 파서는 사이트 종속이 아니라 **법원 표준 양식**을 전제로 짠 것으로 보여서, 궁합이 좋을 가능성이 높다.

### ⚠️ 확인됨 — `daejangauction-pdf`(물건 요약 페이지) 경로는 지금 그대로 쓰면 깨진다
"어떻게 실제 PDF를 만들 것인가"를 검증하려고, 로그인한 상태에서 보스옥션 물건 요약 페이지(`landview.html`)를 CDP `Page.printToPDF`로 직접 PDF화해봤다. `pdftotext -layout`로는 그럭저럭 읽히는데, **이 저장소가 실제로 쓰는 `pdf-parse` 라이브러리로 돌려보니 입찰진행내용 표 전체와 토지면적·건물면적·감정가·보증금 등 핵심 숫자가 통째로 빠졌다**(아래 "앞부분" 참고). `daejang-auction-pdf-parser.ts`가 찾는 `구분 입찰기일 최저매각가격 결과` 패턴도 매칭 실패.

```
사건내용   대전지방법원 경매3계 | 매각기일 2026-11-04(10:00)
...
물건종별  근린주택   사건접수  2026.01.12  토지면적  ㎡ (평)        ← 숫자 소실
경매구분  임의경매   건물면적  ㎡ (평)     배당종기일 2026-04-21    ← 숫자 소실
소 유 자  남성호    채 권 자  대전서부새마을금고  채 무 자  남성호
보 증 금  (%)       감 정 가            최 저 가  (%)             ← 전부 소실
매각조건  대항력있는임차인, 임차권등기
[입찰진행내용 표 전체가 통째로 빠짐]
```

원인 추정: 이 페이지는 숫자·표 일부를 캔버스/차트 위젯(공시지가 분석 그래프 등)과 섞어 그리는 구간이 있어, 브라우저 인쇄로는 레이아웃이 비슷해 보여도 PDF 텍스트 레이어가 깨지는 것으로 보인다(완전히 확인된 원인은 아님). **이 경로(물건 요약 페이지 전체를 PDF화)는 추가 조사 없이는 신뢰할 수 없다** — `daejangauction-pdf` 파서를 그대로 쓰려면 별도 해결책이 필요하다.

### ❓ 미검증 — 다음에 바로 이어서 확인해야 할 것
등기(건물) 뷰어의 실제 "다운로드" 버튼으로 **진짜 PDF 파일**(스크린샷이 아니라)을 받아서, 이 저장소의 `parseRegistryRights`에 실제로 통과하는지까지 확인하려던 중 **보스옥션 로그인 세션이 또 만료**(1시간 제한)되어 중단했다. 다음 작업 세션에서 재로그인 후 가장 먼저 해야 할 검증.

## 4. 제안 아키텍처

```
[다가구경매파이프라인 — 로컬]                [AuctionFlow Pro — 이 저장소]
법원 리스트업 → 물건 선택                                  │
    │                                                      │
    ▼                                                      │
보스옥션 개별 문서 뷰어에서                                  │
"다운로드" 버튼으로 실제 PDF 저장    ──POST /api/pdf-to-case──▶  사건 생성/보강
(매각물건명세서·등기 2종·감정평가서)                          │
registry-building/registry-land/                            │
tenant-report/appraisal-report로 kind 지정                   │
```

- **daejangauction-pdf(물건 요약 페이지) 경로는 1단계에서 제외한다.** 지금 당장 고치려 하지 않고, 개별 문서 4종(등기 2종·매각물건명세서·감정평가서)부터 연결한다 — 이미 작동 확인된 데이터 소스만 쓴다.
- 연결 방식은 처음엔 **사람이 한 단계 다리 역할**(로컬에서 받은 PDF를 AuctionFlow Pro의 "PDF로 물건 추가" 화면에 드래그)부터 시작하고, 안정화되면 로컬 스크립트가 `/api/pdf-to-case`를 직접 호출하는 자동 연결로 넘어간다. 처음부터 완전 자동화하지 않는 이유: 두 프로젝트가 서로 다른 세션에서 독립적으로 개발됐고, 이 저장소는 CLAUDE.md에 명시된 **사용자 데이터 보호 규칙**(파괴적 변경 전 스냅샷 등)이 있는 운영 중인 앱이라 신중하게 단계를 밟는 편이 안전하다.

## 5. 데이터 보호 — 이 저장소의 기존 규칙과의 관계

이 저장소 `CLAUDE.md`의 사용자 데이터 보호 규칙(파괴적 변경 전 스냅샷, 빈 목록에 시드 자동 주입 금지 등)은 **기존 사건 데이터를 건드리는 변경**에 적용된다. 이번 통합은 `POST /api/pdf-to-case`로 **새 사건을 추가**하는 경로만 쓰므로 그 규칙과 충돌하지 않는다 — 다만 실제 구현 단계에서 혹시 기존 사건에 문서를 "병합"하는 흐름을 추가한다면(예: 같은 사건번호면 자동 병합), 그 부분은 파괴적 변경 규칙을 반드시 다시 확인해야 한다.

개인정보: 등기부·매각물건명세서에는 소유자·임차인 실명과 주민등록번호 일부가 그대로 들어있다. 두 프로젝트 모두 로컬 전용(`다가구경매파이프라인`)이거나 본인 전용 앱(AuctionFlow Pro, Supabase 계정 분리)이라 이 통합 자체는 문제가 없지만, **다가구경매파이프라인의 공개 문서 사이트(`dagagu-auction-docs`)에는 이 PRD나 실제 사건 데이터를 올리지 않는다** — 이미 그렇게 하고 있음.

## 6. 열린 질문 (사용자 결정 필요)

1. **연결 방식**: 처음부터 "사람이 업로드"로 시작할지, 바로 API 자동 호출(로컬 스크립트 → `/api/pdf-to-case`)까지 만들지?
2. **대상 서버**: 로컬 `npm run dev`(localhost:3000)로 테스트할지, 배포된 Vercel URL로 바로 보낼지? (인증·CORS 설정이 달라짐)
3. **daejangauction-pdf 경로**: 지금 발견한 숫자 소실 문제를 더 파볼지(원인 규명), 아니면 당분간 포기하고 개별 문서 4종만으로 충분히 가치 있다고 보고 넘어갈지?
4. **데이터 병합 정책**: 같은 사건번호로 여러 번 문서를 추가하면 하나의 사건에 계속 누적할지, 매번 새 사건으로 만들지?
