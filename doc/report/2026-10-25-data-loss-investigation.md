# 점검 리포트 — 물건 목록 소실 조사 (2026-10-25)

> 목록이 사라졌고 백업도 없다는 보고를 받아, 브라우저 저장소 파일을 읽기 전용 복사본으로 분석했다. **정확한 원인은 밝히지 못했다.** 사실과 추정을 구분해 적는다.

## 1. 조사 방법

- 사용 중인 브라우저의 저장소(localStorage·IndexedDB LevelDB 파일)를 작업 폴더로 복사해 읽었다(원본은 건드리지 않음).
- LevelDB 라이브러리로 현재 값을 읽고, 테이블 파일을 직접 해석해 삭제·덮어쓴 이전 값이 남아 있는지 확인했다.
- 활동 기록(`activity-log`), 서버 수집 폴더, 개발 서버 로그, 시간 백업·클라우드 동기화 설정을 확인했다.

## 2. 확인된 사실

| 관찰 | 의미 |
|---|---|
| 현재 저장소의 물건은 3건뿐이고 모두 15:19 이후에 새로 만든 것 | 현재 목록은 소실 이후에 다시 쌓인 것 |
| 활동 기록에 같은 날 10:25~14:49에 스크리닝한 서로 다른 물건 약 20건이 남아 있음 | 그 시간대에 약 20건이 있었고 지금은 없음 → **14:49~15:19 사이에 목록이 비워짐** |
| 「새로 시작」 기록(`data-epoch`)이 없음 | 「처음부터 새로 시작」이 실행된 것은 아님(그 기능은 마지막에 이 기록을 남김) |
| 사진·문서 보관소(IndexedDB)의 소실 이전 파일이 남아 있음 | 보관소 삭제는 아니고 **목록(localStorage)만 비워진 것으로 보임** |
| 서버의 수집 원본 폴더가 8개만 남음 | 일부 원본은 별도로 지워졌음(원인 미확인) |
| 브라우저 백업(IndexedDB)에 백업 기록이 없음 | 백업이 만들어지지 않았거나 이미 지워짐 |
| 시간 백업·클라우드 동기화(Supabase) 미설정 | 다른 복사본 없음 |
| 같은 브라우저에 `localhost:3001`·`3005`·배포 주소별로 따로 쌓인 옛 데이터(5~9월, 1~9건) | 주소·포트마다 저장소가 갈라져 목록이 없어 보이는 일이 반복됐을 가능성 |
| 이전 값은 마지막 2개 버전만 남아 있고 모두 3건 | 소실 전 데이터는 저장소 파일에서 복구할 수 없었음 |

## 3. 후보 원인 (확정 아님)

1. **브라우저 저장 한도 근접**: 물건 36건이 한도의 약 97%였다. 한도를 넘으면 저장이 실패하거나 문서 글자를 줄여 저장하는데, 그 경로에서 오래된 값으로 되돌아갈 수 있다.
2. **불러오기 실패 후 빈 상태가 저장됨**: 데이터 해석에 실패하면 빈 기본값으로 시작해 원본을 덮어쓸 수 있는 구조였다(이후 보호 장치로 막음).
3. **주소·포트 변경**으로 다른 저장소가 열림.
4. 사용자 조작(전체 삭제·일괄 삭제 등) — 증거는 찾지 못했다.

## 4. 대응 (같은 날 구현)

- **디스크 백업**(브라우저 밖), **저장 보호 장치**(읽기 실패 시 저장 중지·원본 보존, 급감 전 원본 보존), **복구 배너**, 「새로 시작」 직전 백업 — [데이터 보호 설계](../spec/DATA-PROTECTION-DESIGN.md)
- **저장 용량 줄이기**로 한도 근접 문제 완화(약 63% 감소) — [저장 용량 설계](../spec/STORAGE-SLIM-DESIGN.md)
- 활동 기록에서 소실된 것으로 보이는 물건 17건의 사건번호를 로컬 파일에 정리해 태인 검색에서 다시 등록할 수 있게 함(공개 문서에는 싣지 않음).
- 같은 날 이 대응 과정에서 만든 **저장 차단 버그**(저장된 값이 없는 브라우저를 오류로 오판)를 발견해 수정했다.

## 5. 교훈과 남은 위험

- 백업은 데이터와 **다른 저장소**에 있어야 한다(같은 브라우저 저장소는 함께 사라진다).
- 복사본이 외장 SSD 한 곳이라 내부 디스크에 한 부 더 두는 작업이 필요하다.
- 브라우저 저장 한도는 계속 위험 요인이다 → IndexedDB 이전(2단계)과 디스크 기준 저장소(3단계)를 계획.
- 소실 원인은 미확인이므로, 다음에 목록이 비면 디스크 백업에서 복구되는지 먼저 확인하고 그때의 상황(주소·직전 작업)을 기록해 원인을 좁힌다.
